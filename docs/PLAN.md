# Project plan

This is the whole-project plan. Issues #1 (data pipeline and repo foundation), #2
(baselines), #3 (scikit-learn models), #4 (gradient boosting) and #5 (SHAP
explanations and the SNAP lift) are built, with the evaluation harness. Everything marked **not built** below is planned work, and every number in the
"Targets" section is a target, not a result.

## 1. Purpose

Show end-to-end retail demand forecasting on the real Walmart M5 data: download and
verify the data, engineer features, compare simple and strong models, and explain the
winner. The point is an honest evaluation harness - verified inputs, no look-ahead,
walk-forward validation, the competition's own metric - not a leaderboard chase.

## 2. Data (built)

- Source: the Kaggle "M5 Forecasting - Accuracy" competition (Walmart). 30,490 daily
  series: 3,049 products x 10 stores in 3 states (CA, TX, WI), 1,941 days of sales
  (2011-01-29 to 2016-05-22), plus a 1,969-day calendar with events and per-state SNAP
  days, and weekly sell prices.
- Mirror: the four files are fetched from the public HuggingFace dataset
  `denephew/M5_Forecasting` (license field: cc) at a pinned revision.
- Provenance: `provenance/m5_data.json` records each file's URL, sha256 and size.
  `m5-download` refuses files whose hash differs, then checks the documented facts above
  (series, products, stores, states, days, calendar length, submission rows). If any
  check fails it stops; nothing runs on unverified data. `m5-features` re-checks both
  before building.
- Subset: one store, default `CA_1` (about 3,049 series), chosen with `--store`. The
  store is recorded in the feature table and in `results/features_<store>_manifest.json`.
- Raw data lives in the gitignored `data/` directory and is never committed.

## 3. Method

- Horizon: 28 days, as in the competition. Sales-derived features use only sales at
  least 28 days old, so one model forecasts all 28 days directly (built).
- Leakage: `tests/test_leakage.py` scrambles every input after a cutoff and fails if any
  feature on or before the cutoff changes (built; it also passed on real CA_1 data).
- Walk-forward validation over the real calendar: 3 folds, each training on all days
  up to a cutoff and forecasting the next 28 days; the last fold ends on the last day of
  sales (built, `src/m5/evaluation.py`). `tests/test_backtest.py` checks that no
  model's forecast changes when every sale after the cutoff is scrambled.
- Metric: the competition's WRMSSE over its 12 levels (scale from the training period,
  weights from dollar sales in the last 28 training days), plus RMSSE and MAE per series
  for diagnosis (built). On one store the 12 levels reduce to 4 distinct ones (total,
  category, department, item). Baselines are computed first so every model has a
  reference.

## 4. Models, in issue order

1. Baselines (#2, built): seasonal-naive and a simple linear regression.
2. scikit-learn (#3, built): Ridge regression, plus LogisticRegression only where a
   classification framing genuinely applies: "will this item sell today", used as the
   zero part of a hurdle model. The authoritative list is `MODELS` in
   `src/m5/models.py`.
3. Boosting (#4, built): XGBoost and LightGBM with Tweedie loss on the same features
   and folds. Hyperparameters come from a small grid (Tweedie variance power x tree
   size) searched inside each fold's training days: train through the cutoff minus 28
   days, score WRMSSE on the last 28 training days, pick boosting rounds by early
   stopping there, then refit the best candidate on every training day. The test
   window never takes part. The grid, the fixed parameters and every candidate's score
   are recorded in `results/metrics.json`.

Features (built): 52 model inputs across the planned families, meeting the 40+ target -
12 sales lags, rolling mean and std over 6 windows, zero-sales share, same-weekday mean,
days since release, 7 price features, calendar and event fields, and the store's state
SNAP flag. The authoritative list is `feature_columns()` in `src/m5/features.py`.

## 5. Tracking and artifacts (**not built** unless noted)

- MLflow for every training run (built, local store in the gitignored `mlruns/`).
- `results/metrics.json`: WRMSSE per model per fold, with versions, seed, fold
  boundaries and runtime; `results/metrics.md` is the readable table (built).
- A forecast-vs-actual plot, `results/forecast_vs_actual_<store>.png`, drawn by
  `m5-plots` from `results/metrics.json` (built).
- SHAP summary plots, `results/shap_summary_<model>_<store>.png`, and a mean |SHAP|
  chart, `results/shap_importance_<store>.png`, drawn by `m5-explain` (built).
- The SNAP lift: how much more food sells on SNAP days, computed from the data, not the
  model: `results/snap_lift.json` from `m5-explain` (built).
- Every published number is regenerated by a script and never hand-edited. Built so far:
  `results/features_<store>_manifest.json` from `m5-features`, `results/metrics.json`
  and `results/metrics.md` from `m5-backtest`, `results/forecast_vs_actual_<store>.png`
  from `m5-plots`, `results/shap_summary.json`, `results/snap_lift.json`,
  `results/explanations.md` and the SHAP plots from `m5-explain`.

## 6. Explainability (built, issue #5)

SHAP on both boosted models (they are within 0.002 WRMSSE of each other): global
feature importance, a few series-level readings, and where the model is fragile (for
example new items or intermittent sellers). `m5-explain` rebuilds each fold's model
from `results/metrics.json`, requires it to reproduce the recorded WRMSSE, and computes
exact TreeSHAP for every test-window row. `src/m5/explain.py` and `src/m5/snap.py`
document the method; `docs/RESUME_CLAIMS.md` has the measured findings.

## 7. Repo layout and running it

- `src/m5/`: `download.py`, `verify.py`, `data.py`, `features.py`, `leakage.py`,
  `pipeline.py`, `config.py`, `evaluation.py`, `models.py`, `backtest.py`, `plots.py`,
  `explain.py`, `snap.py`.
- `tests/`: pytest suite on a synthetic fixture (`tests/fixtures/synthetic_m5/`).
- `provenance/`, `results/`, `docs/`.
- End to end today: `uv sync`, `uv run m5-download`, `uv run m5-features`,
  `uv run m5-backtest`, `uv run m5-plots`, `uv run m5-explain`. CI runs ruff,
  mypy and pytest on every push and pull request.

## 10. Honesty rules

- Targets, not results: LightGBM about 0.62 WRMSSE vs about 0.85 for seasonal-naive
  (about 27% lower error), Ridge about 0.75, SNAP lift about 10% on food. Report what is
  measured, even when it misses these.
- Never skip, deselect, xfail or loosen a test or gate to get green.
- Never fabricate data, metrics or reference values. The synthetic test fixture never
  produces a published number.
